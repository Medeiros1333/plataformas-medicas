## 1. Metodologia de extração de questões (pipeline de 3 camadas)

Depois de várias tentativas falhas (ver seção 3), o processo que funciona é:

**Camada 1 — Extração mecânica (determinística, sem LLM, sem custo de API):**
1. `pdftotext -layout -enc UTF-8 <prova>.pdf` → preserva posição espacial (2 colunas).
2. `dados/_scripts/reordenar_colunas.js` → separa cada linha em coluna esq./dir. pelo maior
   espaçamento (≥3 espaços) e concatena col.esquerda-completa + col.direita-completa por página
   (delimitada por form-feed `\f`). Isso resolve o embaralhamento de 2 colunas que a extração
   simples (sem `-layout`) produz.
3. `dados/_scripts/extrair.js <ano> <edicao> <arquivo_prova.txt> <arquivo_gabarito.txt> <n_esperado>`
   → separa por questão (`QUEST[ÃA]O\s*N`), tenta 3 formatos de alternativa (parênteses, letra
   isolada em linha própria, letra isolada inline sem exigir maiúscula depois — ver código),
   casa com gabarito (3 formatos de gabarito também suportados: lista número+letra, grade
   Questão/Gabarito, formato colado "1B"). Gera `dados/raw/{ano}.{edicao}.pre.json`.
4. Resultado típico: ~70-95% das questões saem "ok" (enunciado+alternativas limpos) direto
   dessa camada, sem gastar nenhum token de LLM.

**Camada 2 — Correção pontual de casos ilegíveis:**
- Gabaritos que não extraem como texto (fonte quebrada ou resposta desenhada): ler a página do
  PDF original visualmente (Read tool renderiza PDF como imagem) e transcrever manualmente para
  um arquivo `dados/raw_text/{ano}__Gabarito_VISUAL.txt` no formato simples "número letra".
- Questões com pouco texto (`status:"revisar_extracao"`) ou números ausentes do array: reler o
  texto bruto capturado (já está no campo `enunciado`, só não separado em alternativas) ou, se
  necessário, abrir a página específica do PDF original.

**Camada 3 — Classificação (Fase B, precisa de julgamento clínico):**
- Para cada questão: `especialidade_primaria`, `especialidade_secundaria[]`, `tema`, `assunto`
  (específico, não genérico), `competencia`, `dificuldade_estimada` (1-5).
- Feito em lotes por EDIÇÃO (100-110 questões), nunca a prova inteira misturada com extração.
- Ver `dados/_taxonomia_e_instrucoes.md` seção "FASE B" para o prompt exato usado.

**Consolidação:** `dados/_scripts/consolidar.js` lê todos os `dados/raw/*.json` finais, gera
`dados/mapa_mestre.json` (índice compacto) e `dados/modulos.json` (agrupamento por
especialidade+tema, com código, tier, prioridade calculada, lista de `questoes_ids`). Roda de
novo automaticamente toda vez que novas edições forem classificadas — **não precisa ser
reescrito, só reexecutado**.

**Scripts de apoio para classificação eficiente (economizam tokens):**
- `dados/_scripts/compactar.js <ano.edicao>` → dump de texto simples (não-JSON) de um
  `.pre.json`, bem mais barato de ler do que o JSON pretty-printed inteiro.
- `dados/_scripts/mesclar_classificacao.js <ano.edicao> <classificacao.json> [correcoes.json]`
  → aplica um mapeamento compacto `{numero: {especialidade...}}` de volta no `.pre.json`,
  gerando o `.json` final. Evita ter que reemitir o enunciado/alternativas inteiros ao
  classificar — só a classificação (curta) precisa ser gerada.

## 1.1 Ferramentas de fluxo de trabalho (adicionadas em 2026-08-13)

Até esta sessão, 3 passos do processo eram feitos manualmente/de olho a cada lote: (a) checar se um
módulo candidato é duplicata semântica de um já `"gerado"`, (b) conferir se o gabarito escrito em
cada questão bate com o bruto do banco, (c) escolher os próximos candidatos por prioridade. Os 3
viraram scripts em `dados/_scripts/`:

- **`detectar_duplicatas.js`** — normaliza `tema` (remove acento, stopwords PT-BR, ordena tokens em
  bag-of-words) e compara cada candidato `nao_gerado` contra TODOS os módulos `gerado` (qualquer
  especialidade — pega duplicata cruzada como PED-45/CAR-02 do erro #54) e entre si. Classifica em
  "forte" (containment ≥0.85 E Jaccard ≥0.5 — o duplo gate evita que um tema guarda-chuva de 1
  palavra tipo "Trauma" dispare falso-positivo contra toda uma família de subtemas) ou "possível".
  **Limitação conhecida, sem stemming:** "Hérnias" (CIR-02) e "Hérnia" (CIR-44) contam como tokens
  diferentes e não geram match algum — foi assim que a duplicata CIR-44/CIR-02 escapou da varredura
  automática no lote 4 e só foi pega por leitura manual do conteúdo antes de gerar. **Lição: rodar o
  script SEMPRE, mas nunca como substituto da leitura crítica do conteúdo real — só como primeiro
  filtro.**
- **`verificar_gabaritos.js`** — compara o `gabarito_oficial` escrito em cada
  `_conteudo_<CODIGO>.json` (já processado por `preparar_conteudo_modulo.js`) contra o bruto em
  `mapa_mestre.json`, para um lote inteiro de códigos de uma vez. Só pega erro de TRANSCRIÇÃO
  própria (a fonte é a mesma), não gabarito errado na fonte — as duas checagens continuam
  necessárias em paralelo (lição já estabelecida no erro #24).
- **`selecionar_lote.js N`** — escolhe os N candidatos `nao_gerado` de maior prioridade/volume,
  excluindo automaticamente os que dariam duplicata forte contra o já `gerado` ou contra outro
  candidato do mesmo lote (mas não substitui a checagem de conteúdo — ver limitação acima).
- **`_checklist_geracao_modulo.md`** — versão condensada e acionável da "constituição" do projeto
  (estrutura obrigatória, regras de veracidade, regras de manuseio de questões do banco), pensada
  para ser lida por um subagente no início de cada módulo sem precisar processar o
  `PROCESSO_E_APRENDIZADO.md` inteiro (que já passa de 250 linhas densas). Mantida sincronizada
  manualmente com este arquivo — se uma lição nova mudar uma regra operacional, atualizar os dois.

**Achado ao rodar `verificar_gabaritos.js` pela primeira vez em TODO o Hub publicado (não só num
lote novo):** revelou 16 cards de questão pré-existentes com `alternativas: {}` — quebrados
silenciosamente no Hub. A causa não era falta de dado, era um cabeçalho `**[INEP ...]**` mantido em
questões que o próprio texto já dizia serem "sem alternativas recuperáveis" (ver erro novo abaixo).
Isso reforça: **rodar as ferramentas de verificação em todo o Hub de vez em quando (não só no lote
que acabou de ser gerado) é a forma barata de achar regressões silenciosas** — nenhum desses 16
casos tinha sido notado nas verificações de fim de lote anteriores, porque elas só cobriam os
códigos daquele lote específico.

## 2. Padrão de módulo de estudo (baseado no INF-01, aprovado pelo usuário)

O usuário validou explicitamente o módulo `modulos/INF-01_meningites-bacterianas.md` como
padrão de qualidade: **"o conteúdo de meningite está muito bom... com ele eu consigo saber
tudo o que importa da patologia para a prova"**. Este é o critério de aceitação para TODOS os
módulos seguintes — não é só sobre formato, é sobre PROFUNDIDADE (o módulo tem que ensinar a
patologia inteira, não só comentar as questões).

**Checklist obrigatório por módulo** (replicar a estrutura exata do INF-01):
1. **Cabeçalho** com código, especialidade, tema, tier, nº de questões históricas (ser honesto
   se a amostra é parcial — ver nota padrão usada no INF-01), tempo estimado, pré-requisitos.
2. **Teoria** — texto corrido (não bullets soltos): epidemiologia por subgrupo relevante,
   fisiopatologia no nível necessário pra raciocinar, classificações em tabela, quadro clínico
   com sinais discriminantes, diagnóstico exame-por-exame com indicação/achado/limitação,
   tratamento esquema-por-esquema em tabela (fármaco/dose/via/duração — usar ⚠️ VERIFICAR
   sempre que a dose não puder ser confirmada com certeza, NUNCA inventar número), situações
   especiais (gestante/criança/idoso/renal crônico/imunossuprimido), caixa 🇧🇷 quando MS diverge
   de diretriz internacional, caixa ⚠️ PEGADINHA DO INEP, referências numeradas ao final.
3. **Prática clínica real** — como aparece no plantão de verdade, tabela de fármacos em ORDEM
   DE FREQUÊNCIA DE USO REAL (não alfabética) com apresentação/dose adulto/dose pediátrica
   mg-kg/ajuste renal-hepático/efeito adverso/interação, prescrição-modelo pronta, erros reais
   que médicos cometem, o que dizer ao paciente, checklist da ESTAÇÃO PRÁTICA (2ª etapa).
4. **Questões do INEP** — TODAS as questões do banco vinculadas a este `modulo_destino`,
   comentadas alternativa por alternativa (por que a certa está certa E por que cada errada
   está errada), com "o que a banca estava testando". Nota honesta se a amostra do banco ainda
   é parcial (nem todas as 18 edições foram classificadas ainda).
5. **Flashcards** — bloco ` ```tsv ` com Frente\tVerso\tTags, 15-40 cards, 1 fato por card,
   tags no formato `Revalida::Especialidade::Tema::Subtema`. Doses só viram card se a fonte
   estiver confirmada (não gerar flashcard de dose com ⚠️ VERIFICAR pendente).
6. **Resumo de fixação** — 5 frases-chave, tabela-síntese, doses essenciais (ou aviso de que
   foram omitidas por falta de fonte confirmada), fluxograma textual, 3 erros mais comuns,
   conexões com outros módulos.
7. Bloco `<!-- METADADOS -->` em JSON ao final com `itens_a_verificar[]` listando toda ⚠️
   pendência do módulo — isso vira o backlog de correção da seção 4 deste arquivo.

**Depois de escrever o `.md`, sempre gerar em sequência:**
```
node dados/_scripts/preparar_conteudo_modulo.js "<CODIGO>" "modulos/<arquivo>.md" > dados/_scripts/_conteudo_<CODIGO>.json
```
e então injetar no Hub (ver seção 5) + extrair o bloco de flashcards para `anki/<CODIGO>_<slug>.tsv`
(o mesmo texto que está entre \`\`\` na seção 4 do `.md`, é literal, não precisa reformatar).

**IMPORTANTE (feedback do usuário, 2026-07-29):** as questões dentro do Hub NÃO devem
aparecer já respondidas/reveladas. O comportamento correto (já implementado no Hub) é modo
simulado: mostra enunciado + alternativas clicáveis, sem gabarito nem comentário visíveis; só
depois que o usuário clica numa alternativa é que o sistema revela acerto/erro + comentário +
botão "tentar novamente". Isso é automático — o `.md` do módulo continua trazendo o gabarito e
comentário no texto (para leitura), é só o HUB que esconde até responder.

## 5. Como continuar gerando módulos (procedimento operacional)

1. Ler `dados/modulos.json`, filtrar por `status_geracao:"nao_gerado"`, ordenar por `prioridade`
   desc — são os próximos candidatos.
2. Para o módulo escolhido, buscar as questões completas: `questoes_ids` do módulo → localizar
   cada uma nos arquivos `dados/raw/{ano}.{edicao}.json` correspondentes (o `id` já entrega
   ano/edição, ex. `INEP2013-1-Q068` → `dados/raw/2013.1.json`).
3. Escrever o `.md` em `modulos/<CODIGO>_<slug-do-tema>.md` seguindo EXATAMENTE o checklist da
   seção 2 — usar `modulos/INF-01_meningites-bacterianas.md` como referência de nível de
   detalhe, não só de formatação.
4. Gerar `anki/<CODIGO>_<slug>.tsv` a partir do bloco de flashcards do `.md`.
5. Rodar `preparar_conteudo_modulo.js` (seção 2) e injetar no Hub (mesmo padrão do script usado
   para o INF-01: ler `dados/_scripts/_conteudo_<CODIGO>.json`, fazer merge no objeto
   `CONTEUDO_MODULOS` já existente no `hub/revalida_hub.html`, republicar via Artifact tool).
6. Atualizar `status_geracao` para `"gerado"` no `modulos.json` daquele módulo.
7. Marcar o item correspondente como concluído neste arquivo/TodoWrite.
